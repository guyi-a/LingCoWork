# 项目四 · 长对话上下文压缩

> 对应简历第四条 bullet：「长对话上下文压缩」。
>
> 核心模块：上下文压缩中间件、token 估算器、摘要生成器和历史投影器。

---

## 一、先对照简历：上下文压缩怎么实现

Agent 的对话历史不只有聊天文字，还包含读文件结果、命令输出、检索内容和工具调用记录。
对话持续几十轮后，这些内容会逐渐撑满模型的上下文窗口。

我们的实现可以拆成六步：

```text
1. Agent run 内每次调用模型前，压缩中间件取得当前消息列表

2. 估算当前上下文占了多少 token
   没超过阈值 → 不处理，直接继续
   超过阈值   → 进入压缩

3. 选择一段较早的完整历史
   切点不能落在 tool_call 和 tool_result 中间
   最近的用户请求和正在进行的任务不参与折叠

4. 调用独立摘要模型
   生成一份五段式结构化摘要：
   用户意图、任务进展、待办计划、技术要点、下一步交接

5. 用摘要替换当前 run 中被折叠的旧消息
   同时保存“摘要 + 折叠到哪条消息”
   原始消息一条都不删除

6. 中间件把压缩后的消息列表交给主模型
   Agent 继续当前 run，不需要重新开始任务
```

整体链路：

```text
Agent run 准备调用主模型
  ↓
进入上下文压缩中间件
  ↓
读取当前消息列表，估算 token
  ↓
没超过：原样交给主模型
超过了：较早历史 → 摘要模型 → 结构化摘要
  ↓
中间件重写当前消息列表：
结构化摘要 + 未折叠的最近历史
  ↓
主模型继续当前 Agent run
```

面试开场可以直接这样说：

> 我们把上下文压缩做成 run 级中间件，在 Agent 每次调用主模型前检查当前消息列表。超过阈值
> 后，中间件选择较早且完整的一段历史，交给独立摘要模型生成包含用户意图、任务进展、待办、
> 技术要点和下一步交接的结构化摘要，再用摘要替换当前上下文里的旧消息。原始消息不删除，
> 只额外保存摘要和折叠位置；后续再次超限时，把上一份摘要和新增历史一起重新总结。

这段说完，面试官如果继续追问，再讲下面的细节。

## 二、为什么要压缩

假设 Agent 连续工作了几十轮：

```text
用户需求
助手分析
读取 5 个文件，每个几千行
执行命令，产生大量日志
搜索网页，返回多段正文
修改代码
继续读取和测试
……
```

这些内容每轮都会被重新发给模型。最终会出现三个问题：

1. **超过模型窗口**：请求被拒绝，或者历史被粗暴截断。
2. **成本和延迟越来越高**：每轮都要重复发送大量旧内容。
3. **有效信息被噪声淹没**：长上下文中间的信息更容易被模型忽略。

压缩的目标不是把历史全部删掉，而是：

> 人仍然能看到完整历史，模型只携带一份足够继续工作的摘要。

## 三、什么时候触发

### 每次调用主模型前检查

压缩中间件挂在 Agent run 的模型调用前。一次 run 里可能连续发生多次“模型推理 → 工具调用
→ 工具结果 → 再次推理”，每次重新请求模型前都会检查当前消息列表。

```text
Agent run
  → 调用模型前：压缩中间件检查上下文
  → 模型决定调用工具
  → 工具执行，结果加入消息列表
  → 再次调用模型前：压缩中间件再次检查
  → 模型继续推理
```

这样不仅能处理跨多轮累积的旧历史，也能处理单次长 run 内大量工具输出造成的上下文膨胀。

压缩只选择较早且已经完成的历史，最近的用户请求、当前任务状态以及尚未配对完成的工具调用
必须保留，避免把 Agent 正在处理的指令折叠掉。

### 超过阈值才压缩

阈值不是写死的一个随意数字，而是根据模型窗口计算：

```text
压缩阈值 =
模型名义窗口 × 可用比例
- 给本轮输出预留的 token
- 系统提示词和工具 schema 的缓冲
```

默认配置：


| 配置   | 默认值    | 作用                      |
| ---- | ------ | ----------------------- |
| 模型窗口 | 128000 | 模型名义上下文上限               |
| 可用比例 | 85%    | 不把窗口用满                  |
| 输出预留 | 8000   | 给这一轮回答和工具调用留空间          |
| 固定缓冲 | 4000   | 覆盖系统提示词、工具 schema 等额外内容 |


最终默认阈值是 **96800 token**。

固定缓冲很重要。消息表里只有对话历史，但实际请求还会附带系统提示词、工具定义和运行时注入
内容。只统计消息表，会高估真正还能使用的空间。

## 四、token 怎么估算

没有给整个项目引入 tokenizer，而是采用“精确锚点 + 尾部粗估”。

### 第一步：使用模型返回的精确 usage

模型每次响应都会返回 token usage。主 Agent 每轮最后一条 assistant 消息会保存
`TotalTokens`。

这个数字由模型服务商计算，可以认为是那一时刻的精确上下文大小。

### 第二步：只粗估锚点后的新消息

估算下一轮历史时：

```text
最近一次模型返回的 TotalTokens
+
它之后新增消息的字符数 ÷ 4
```

为什么不直接对全部历史做“字符数除以 4”？

因为中文、英文、代码的 token 比例不同，全量粗估的误差会随着对话不断累积。现在只有最近几条
消息使用粗估，下一轮模型返回 usage 后又会生成一个新锚点，所以误差只存在于很短的尾部。

### 哪些 usage 不计入

子 Agent 的 token usage 不计入主线程。

子 Agent 有自己的私有上下文。它内部跑了多少步，并不代表主 Agent 的对话历史增长了多少。

## 五、哪些消息可以被折叠

不能简单地按消息数量从中间切一刀。

工具调用通常是成对的：

```text
assistant: 我要调用 read_file，tool_call_id = 123
tool:      tool_call_id = 123 的执行结果
```

如果切点落在两者中间，主模型只看到工具调用、看不到工具结果，OpenAI 兼容接口会直接报错。

### 默认做法：折叠此前全部历史

默认 `KeepLastUserTurns = 0`，即把新消息之前的历史全部折叠。

这之所以安全，是因为一轮运行产生的 assistant 消息和 tool 消息会作为一个批次原子落库。
新一轮开始时，数据库里保存的是完整回合，不会只落下一半工具调用。

### 如果需要保留最近 K 轮

切点必须回退到某条 user 消息之前。

user 消息代表一个新回合的开始，切在它前面，不会把工具调用和工具结果拆开。

还有两道保护：

- 如果历史只有一个尚未回答的用户问题，不压缩。
- 回放时如果仍发现没有结果的孤儿 tool call，剥掉该调用，避免模型 API 报错。

## 六、摘要是怎么生成的

摘要不是让主 Agent 自己顺手写，而是调用一个独立、无工具的摘要模型。

### 为什么不用主 Agent

摘要只是一次“输入历史、输出文本”的简单调用，不需要：

```text
工具调用
多 Agent 编排
流式输出
审批
多轮 ReAct
```

所以使用轻量的 OpenAI 兼容 HTTP 客户端，默认接 DeepSeek，温度设为 0。

### 为什么摘要模型不能挂工具

摘要输入里包含大量过去的工具调用记录。模型可能顺着历史继续执行任务，而不是生成摘要。

提示词可以告诉它“只总结，不要继续做事”，但更可靠的做法是**根本不给它工具**。

这是一个重要的设计原则：

> 能用机制禁止的事情，不只靠提示词请求模型自觉。

### 输入怎么处理

真实的 tool call 和 tool result 会先转成普通文本：

```text
[tool calls] read_file(...)
[tool result: read_file]
文件内容……
```

这样摘要模型只需要理解发生了什么，不需要满足模型 API 对工具消息配对的格式要求。

过大的工具输出也会截断：超过 48000 字符时，只保留头尾各 8000 字符。截断只发生在摘要
输入中，数据库里的原始工具结果不变。

### 输出固定为五段

```text
1. User Intent
2. Task Progress
3. Current Plan & Open Items
4. Key Technical Context & Recall Anchors
5. Handoff
```

对应内容：


| 部分                | 保留什么                        |
| ----------------- | --------------------------- |
| User Intent       | 用户提出过什么需求、如何改口；最近请求尽量保留原文   |
| Task Progress     | 已完成什么、改过哪些文件、运行过哪些命令、遇到哪些错误 |
| Plan & Open Items | 已完成和待完成事项、下一步约束             |
| Technical Context | 路径、函数、接口、版本、端口、关键代码和错误原因    |
| Handoff           | 下一轮首先该做什么                   |


固定结构的作用是把摘要从“自由发挥”变成“按清单交接”，减少模型遗漏关键状态。

## 七、为什么原始消息不删除

压缩采用 append-only：

```text
原消息表：完全不修改

压缩记录：
ThroughSeq       折叠到第几条消息
Summary          结构化摘要
ReplacedCount    替代了多少条消息
EstimatedTokens  压缩时估算的 token 数
```

给模型读取历史时再做投影：

```text
数据库原始历史：
消息 1、消息 2、消息 3……消息 100、新消息

压缩记录：
消息 1～100 由摘要 A 表示

模型实际看到：
摘要 A + 新消息
```

这样做有三个直接收益：

1. **UI 不受影响**：用户仍能查看完整聊天记录。
2. **可回退、可审计**：摘要丢了信息，原文仍然存在；删除压缩记录即可恢复。
3. **压缩失败无害**：没有生成压缩记录，就继续使用原始历史。

需要准确区分两句话：

```text
原始历史没有被删除       是无损保存
模型看到的结构化摘要     是有损压缩
```

所以更准确的说法是“原始历史零删除”，而不是“模型上下文零丢失”。

## 八、多次压缩怎么衔接

对话继续增长后，还会第二次、第三次超过阈值。

第二次压缩的输入不是只有新增消息，而是：

```text
上一份摘要
+
上一轮压缩后新增的完整历史
```

摘要提示词为不同部分设置了不同合并规则：

- 用户意图继续累加，不能丢掉早期需求。
- 已完成事项不能无故重新变成待办。
- 技术事实要继承，可以重组但不能静默消失。
- Handoff 每次重新生成，不能照抄旧的下一步。
- 旧摘要里的系统描述不能被误写成用户的新要求。

这就是“滚动压缩”：每次摘要都继承上一次的有效状态，再吸收新发生的历史。

外面还会套一层说明，告诉主模型：

```text
这是更早对话的系统生成摘要
不要重新开始任务
不要要求用户重复摘要里已有的信息
优先根据 Handoff 继续工作
需要精确原文时，重新读取对应文件，不要猜
```

没有这层说明，模型容易把摘要当成用户刚发来的新消息，重新打招呼或者从头开始任务。

## 九、失败时怎么办

上下文压缩是 best-effort，不能成为一轮对话失败的原因。


| 失败情况     | 处理方式            |
| -------- | --------------- |
| 摘要模型调用失败 | 记录日志，本轮不压缩      |
| 摘要返回空内容  | 记录日志，本轮不压缩      |
| 压缩记录落库失败 | 丢弃已经生成的摘要，本轮不压缩 |


第三种最容易被问：

摘要已经生成了，为什么不用一次？

因为这会让当前运行和持久化状态不一致：

```text
当前这一轮模型看到了摘要
刷新或重启后，数据库里却没有这条压缩记录
```

宁可浪费一次摘要调用，也不要使用一个无法跨刷新存活的临时状态。

## 十、前端如何展示

前端不展示摘要正文，而是在折叠位置显示：

```text
上下文已压缩 · 共折叠 N 条消息
```

实时状态通过 SSE 的 `context_compacted` 事件发送；页面刷新后，由消息接口重新合成这个标记。

不展示摘要正文的原因：

- 用户已经可以查看完整原文。
- 摘要是给模型继续工作的内部交接材料。
- 展示 AI 摘要会让用户担心“是不是理解错了”，但目前又没有编辑摘要的操作入口。

## 十一、这套方案的边界

### 摘要调用会增加延迟

触发压缩时，要先额外调用一次摘要模型，主模型才能继续运行。虽然只在超过阈值时发生，但用户
仍会感知到这一步延迟。

可以在接近阈值时提前生成候选摘要，不过需要处理“生成摘要后消息又发生变化”的一致性问题。

### 摘要是有损的

五段式结构和滚动合并规则只能降低信息丢失，不能保证摘要完全准确。

append-only 的意义就是保留原文作为兜底。需要精确内容时，Agent 应重新读取文件或历史来源。

### 还没有摘要质量评估

目前没有量化压缩前后的回答质量。

可以补一组评测：针对早期对话生成事实问题，比较压缩前后回答是否一致。

## 十二、面试怎么讲

### 一分钟版本

> Agent 长对话里不只有聊天内容，还有大量文件读取、命令输出和检索结果，很容易把模型窗口
> 撑满。我们把压缩做成 run 级中间件，每次调用主模型前检查当前上下文：先用模型返回的 token
> usage 做锚点，只对最近新增消息做字符粗估；超过阈值后，选取较早的完整历史，交给独立摘要
> 模型生成五段式交接摘要，再用摘要替换当前消息列表里的旧历史。原始消息不删除，只保存摘要
> 和折叠位置；后续再次超限时，把上一份摘要和新增历史一起重新总结，实现滚动压缩。

### 被问“为什么不直接删掉旧消息”

> 删除后用户看不到完整历史，摘要出错也无法回退。我们采用 append-only，原消息不动，只在
> 读取时为模型投影成“摘要 + 最近历史”，所以 UI、审计和模型上下文是三个不同视图。

### 被问“token 怎么估算”

> 不对全量历史做字符估算，而是使用模型上一轮返回的精确 token usage 作为锚点，只对锚点后
> 新增的几条消息做字符数除以 4 的粗估。这样误差只存在于很短的尾部，不会随着长对话累积。

### 被问“工具调用历史怎么压”

> 切点不能落在 tool call 和 tool result 中间，否则模型接口会报错。中间件只折叠已经完成的
> 历史，并把切点退到 user 消息之前。交给摘要模型前，工具调用和结果会转成可读文本，超大
> 输出只在摘要输入里做头尾截断，原始记录不变。

### 被问“最重要的设计点”

> 一个是 append-only：原始消息不删，压缩只改变模型读取历史的视图。另一个是 best-effort：
> 摘要调用或落库失败都退回完整历史，压缩本身永远不能成为一轮对话跑不起来的原因。

### 被问“有什么不足”

> 摘要本身是有损的，目前还没有量化压缩前后的事实召回质量；另外触发压缩时会增加一次摘要
> 模型调用的延迟。后续要补压缩前后的事实问答评测，并考虑在接近阈值时异步预生成候选摘要。
