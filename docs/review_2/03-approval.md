# 项目二 · 工具审批

> 对应简历第二条 bullet 的后半：「审批判定不依据工具名，而依据工具声明的调用后果」。
> 流式那半在 [02-streaming.md](02-streaming.md)。

---

## 先对照简历：多级审批是怎么实现的

简历里这句话：

> 审批判定不依据工具名，而依据工具声明的调用后果。

真正想表达的是：**我们不是简单地把工具分成“要审批 / 不审批”，而是做了一套按风险分层的
多级审批。**

它分成四层：

```text
第 0 层：先推导 effect
  不直接按工具名判断，而是先把这次调用翻译成“会造成什么后果”

第 1 层：强制确认层
  删除、卸载、接入 MCP、安装 skill、创建定时任务这类操作，任何模式都必须问用户

第 2 层：直接放行层
  纯读、问用户、列配置、搜索 skill 这类没有副作用的操作，任何模式都不问

第 3 层：模式判断层
  剩下这些有一定风险、但不是最高危的操作，再交给 manual / accept-write / auto 三种模式判断
```

所以「多级」不是多个审批人，而是**风险先分层，再按层处理**：

```text
工具调用
  ↓
先算 effect
  ↓
高危操作？        → 一定问
  ↓
无副作用操作？    → 一定不问
  ↓
剩下的中风险操作  → 看当前审批模式
```

每一层具体这样处理：

| 层级 | 代表操作 | 怎么处理 | 为什么 |
|---|---|---|---|
| 第 0 层：effect 推导 | `read_file ./a.md`、`run_command "ls"` | 先翻译成后果，不直接审批 | 同一个工具不同参数风险不同 |
| 第 1 层：强制确认 | `rm`、卸载 skill、接入 MCP、安装 skill、创建定时任务 | 任何模式都问 | 要么不可逆，要么改变 agent 之后的能力 |
| 第 2 层：直接放行 | 读工作区内文件、`ls`、`grep`、搜索 skill、列 MCP 配置 | 任何模式都不问 | 没副作用，问了只会制造审批疲劳 |
| 第 3 层：模式判断 | 工作区写文件、普通命令、外部路径读写、内网请求 | 按 `manual` / `accept-write` / `auto` 处理 | 这些不是最高危，但也不能一概放行 |

第 3 层才会进入三种模式：

| 模式 | 第 3 层怎么处理 |
|---|---|
| `manual` | 剩下的都问，偏保守 |
| `accept-write` | 工作区内文件写入不问；命令、外部路径、内网请求仍然看情况，多数要问 |
| `auto` | 普通中风险操作放行；但第 1 层的高危操作还是问 |

完整执行链路是：

```text
模型发起工具调用
  ↓
运行时校验工具参数
  ↓
调用工具自己的 resolveEffect(input)
  ↓
得到 effect，例如：
  - 读工作区内文件
  - 写工作区内文件
  - 执行普通命令
  - 执行危险命令
  - 安装 skill
  - 接入 MCP server
  ↓
审批策略按四层规则判断
  ↓
不需要审批：直接执行工具
需要审批：前端展示审批卡
  ↓
用户批准后，执行前再算一次 effect
  ↓
两次 effect 一致，才真正执行
```

面试里可以先这样描述：

> 我们做的是一套多级审批。工具调用进来后，第一步不是直接看工具名，而是先由工具自己的
> `resolveEffect` 根据参数推导这次调用的后果。拿到 effect 后，策略分三层处理：删除文件、
> 安装 skill、接入 MCP 这类高危或能力变更操作永远要问；纯读、搜索、列配置这类无副作用
> 操作永远不问；剩下的中风险操作再交给当前模式判断，比如 `manual` 更保守，`accept-write`
> 允许工作区内文件写入，`auto` 会放行普通操作。这样既不会所有操作都弹窗，也不会因为工具名
> 没见过就误放行。

## 先说人话

Agent 会替用户做事。

有些事只是看一眼，比如读项目里的 `README.md`。  
有些事会改东西，比如写文件、装依赖、执行命令。  
有些事更危险，比如删文件、读用户家目录、接入一个新的 MCP server。

所以工具执行前要先判断：

> 这次操作要不要让用户确认？

这就是审批。

## 为什么不能只看工具名

最容易想到的方案是按工具名分：

```text
read_file    不问
write_file   要问
run_command  要问
```

但这样不准。

同一个 `read_file`，读的东西不一样，风险就不一样：

```text
read_file ./README.md        读项目文件，可以不问
read_file ~/.ssh/id_rsa      读用户私钥，必须问
```

同一个 `run_command`，命令不一样，风险也不一样：

```text
run_command "ls"             只是看目录，可以不问
run_command "rm -rf dist"    删除文件，必须问
```

所以审批不能问「这个工具叫什么」，而要问：

> 这次工具调用到底会造成什么后果？

这个「后果」就是 effect。

你不用把 effect 想复杂，它就是一句后果说明：

```text
读工作区内文件
读工作区外文件
写工作区内文件
执行一个只读命令
执行一个普通命令
执行一个删除命令
安装一个 skill
接入一个 MCP server
```

流程就是：

```text
工具调用
  ↓
先翻译成后果说明
  ↓
审批策略只看后果说明
  ↓
决定问不问用户
```

## 三种模式

审批模式决定「这套系统有多保守」。

| 模式 | 怎么理解 |
|---|---|
| `manual` | 很保守。除了纯读，基本都问 |
| `accept-write` | 接受 agent 在工作区里改文件，但更宽的操作还要问 |
| `auto` | 最大胆。普通操作都放，但不可逆和扩大能力的操作仍然问 |

这里最容易误解的是 `accept-write`。

它不是「所有写操作都放行」，而是：

> 我接受 agent 在当前工作区里改文件。

所以它主要放行的是 `write_file` 这类文件工具对工作区内文件的写入。

命令行不一样。`run_command` 太宽了：

```bash
npm install
curl https://example.com
git push
rm -rf dist
```

它们全都叫命令，但风险完全不同。

所以在 `accept-write` 模式下，命令仍然要先分类：

| 命令分类 | 例子 | `accept-write` 下 |
|---|---|---|
| 只读命令 | `ls`、`cat README.md`、`git log` | 不问 |
| 普通命令 | `npm install`、`mkdir x`、`echo a > b.txt` | 问 |
| 危险命令 | `rm`、`kill`、`git reset --hard` | 问，任何模式都问 |

一句话：

> `accept-write` 接受的是工作区内的文件写入，不是接受所有命令行副作用。

## 真正的判断顺序

审批策略可以理解成下面这几步：

```text
1. 是不是特别危险？
   是 → 一定问

2. 是不是完全没副作用？
   是 → 一定不问

3. 当前是不是 manual？
   是 → 问

4. 当前是不是 auto？
   是 → 不问

5. 剩下就是 accept-write
   工作区内文件写入 → 不问
   其他有风险的操作 → 问
```

这几步里最重要的是前两步。

### 第一步：特别危险的永远要问

有两类操作永远要问，哪怕是 `auto` 模式。

第一类是不可逆操作：

```text
删除文件
强制 git reset
kill 进程
卸载 skill
```

第二类是「扩大 agent 能力」的操作：

```text
接入一个 MCP server
启用一个 MCP server
安装一个 skill
创建或触发一个定时任务
```

这些操作不一定马上删东西，但它们会改变模型下一轮能做什么。

比如接入一个 MCP server 之后，模型下一轮手里就多了一批远程工具。安装一个 skill 之后，
模型下一轮会读到一份陌生人写的说明文档。这不是一次普通工具调用，而是能力边界变了。

所以它们必须问。

### 第二步：完全没副作用的永远不问

有些操作问了也没意义：

```text
读工作区内文件
列目录
grep 项目文件
问用户一个问题
列出已配置的 MCP server
搜索 skill
预览 skill
```

这些不改变用户文件，不扩大权限，也不越过工作区边界。

如果连这种操作都问，用户会被训练成一直点同意。这样真正危险的弹窗出来时，用户也会顺手点。

所以纯读操作在任何模式下都不问，哪怕是 `manual`。

但有个边界：

> 读工作区外的文件，不算纯读。

因为工作区是用户授权给 agent 的范围。读 `~/.ssh`、读别的项目的 `.env`，虽然技术上只是
读，但已经越过边界了。

## 命令行怎么判断

命令行最麻烦，因为一个 `run_command` 可以干任何事。

所以它会被分成三类：

```text
harmless     只读、安全
normal       普通，有副作用或看不准
destructive 破坏性
```

### 怎么找 destructive

危险命令用黑名单抓。

比如：

```text
rm
rmdir
shred
kill
pkill
git reset --hard
git clean
git push --force
```

如果命令里出现这些，就算破坏性操作，任何模式都要问。

### 怎么找 harmless

无害命令反过来，用白名单。

比如：

```text
ls
cat
head
tail
grep
rg
find
ps
git log
git diff
git status
```

但只看命令头还不够。

这条命令看起来是 `cat`，但其实在读用户私钥：

```bash
cat ~/.ssh/id_rsa
```

如果只因为 `cat` 在白名单里就放行，那就出问题了。

所以 harmless 必须同时满足两个条件：

```text
命令头在只读白名单里
参数也都没有越出工作区
```

下面这些都不能算 harmless：

```bash
cat ~/.ssh/id_rsa      # 越出工作区
cat $HOME/.ssh/id_rsa  # 含变量，静态判断不准
cat a.txt > b.txt      # 有重定向，已经会写文件了
```

这些不会直接当成安全操作放行，而是降级成 `normal`，也就是要问。

这套判断不是完整 shell 解析器，它更像一个保守分类器：

> 看得出危险，就拦住；看得出纯读，就放行；看不准，就问人。

## 普通文件读写怎么判断

文件工具比较简单，主要看路径。

```text
读工作区内文件      不问
读工作区外文件      问
写工作区内文件      manual 问，accept-write 不问，auto 不问
写工作区外文件      问
删除文件            永远问
```

这里的关键是「工作区边界」。

用户把一个项目交给 agent，不等于把整台电脑都交给 agent。  
所以项目内读写和项目外读写要分开。

## MCP 和 skill 为什么特殊

MCP 和 skill 不是普通工具。

普通工具通常是「这一次调用做一件事」。

但 MCP 和 skill 会改变 agent 之后的能力。

### MCP

接入一个 MCP server 后，agent 下一轮可能多出一批新工具。

所以：

```text
列出 MCP server        不问
检查授权状态           不问
测试连接               不问
新增 server            问
启用 / 禁用 server     问
移除 server            问
```

新增和启用要问，是因为能力变多了。  
禁用和移除也要问，是因为它改了持久配置。

### skill

搜索和预览 skill 只是看，不问。

安装 skill 要问。

原因不是它写了一个文件这么简单，而是：

> skill 的说明文档会变成模型之后会读的上下文。

也就是说，安装 skill 等于把一份外部内容放进 agent 的行为依据里。它是能力变化，所以要问。

卸载 skill 也要问，因为它会删掉一个已安装能力。

## 批准后为什么还要再算一遍

审批不是工具马上执行。

中间可能隔着用户思考、点击、甚至过很久才回来。

如果审批时看到的是：

```text
写 ./notes.md
```

但真正执行前变成了：

```text
写 ~/.ssh/config
```

那用户批准的就不是实际执行的东西。

所以系统会做一件事：

```text
审批前算一次 effect
执行前再算一次 effect
两次不一样，就拒绝执行
```

这就是防止「审批目标被换掉」。

这个设计要求 effect 推导必须很稳定：

```text
只能根据工具参数来算
不能依赖当前时间
不能查网络
不能读一个随时会变的外部状态
```

不然两次算出来可能天然不同，系统就会误以为目标被换了。

## 怎么减少重复审批

如果用户每次跑 `npm test` 都要点一次，也很烦。

所以有一个「记住这次选择」。

它不是长期授权，只是当前会话里的临时记忆。

系统会给被批准的操作算一个指纹：

```text
读写文件：具体路径
移动复制：源路径 + 目标路径
执行命令：工作目录 + 完整命令
联网请求：域名
MCP 调用：server 名 + 工具名
```

下次同一个操作再出现，就可以不重复问。

但有几条限制：

```text
只记同意，不记拒绝
只在当前会话生效，重启就没了
不可逆操作不允许记住
扩大能力的操作不允许记住
```

为什么不记拒绝？

因为拒绝通常是场景相关的。用户这次说「先别提交」，不代表下次也永远不能提交。

为什么不可逆操作不能记住？

因为第二次删除文件，也值得重新看一眼。

## 用户拒绝后怎么办

用户拒绝一个工具调用时，不应该让整轮对话直接崩掉。

更好的做法是把拒绝当成一条工具结果喂回模型：

```text
这个工具没有执行。
用户拒绝了。
理由是：不要改这个文件。
```

这样模型可以继续往下走：

```text
换一个方案
解释为什么做不了
问用户下一步怎么处理
```

如果直接抛异常，整个 agent run 就结束了，体验很差。

所以拒绝不是系统异常，而是业务结果。

## 面试怎么讲

你可以按这个顺序讲，不要一上来背 effect 分类。

### 版本一：短回答

> 我们没有直接按工具名做审批，因为同一个工具在不同参数下风险不同。比如 `read_file` 读项目
> 文件可以直接过，但读用户家目录就要确认；`run_command` 执行 `ls` 可以直接过，但执行 `rm`
> 就必须确认。所以我们让每个工具先声明这次调用的后果，也就是 effect，再根据 effect 和当前
> 模式决定要不要弹审批。看不准的情况默认问人。

### 版本二：展开一点

> 整体流程是：工具调用先被翻译成一个后果描述，比如读工作区内文件、写工作区内文件、执行
> 普通命令、执行危险命令、安装 skill、接入 MCP server。审批策略只看这个后果，不看工具名。
> 这样即使后面接入第三方 MCP 工具，也不用把所有工具名写死，只要它能声明自己的后果，就能
> 进入同一套策略。

> 模式上分三档：`manual` 比较保守，除了纯读基本都问；`accept-write` 接受工作区内文件写入，
> 但命令和越界操作仍然要看情况；`auto` 普通操作直接放，但删除文件、安装 skill、接入 MCP
> server 这类不可逆或扩大能力边界的操作仍然要问。

### 被追问「accept-write 对命令怎么办」

> `accept-write` 不是接受所有命令的副作用。它主要接受的是工作区内的文件写入。命令行太宽，
> `ls`、`npm install`、`git push`、`rm` 都是命令，所以命令会先分成只读、普通、危险三类。
> 只读命令不问，普通命令要问，危险命令任何模式都问。

### 被追问「shell 怎么判」

> 它不是完整 shell 解析器，而是保守分类。危险命令用黑名单抓，比如 `rm`、`kill`、
> `git reset --hard`；无害命令用白名单，比如 `ls`、`cat`、`grep`、`git log`。但白名单命令
> 还要检查参数不能越出工作区。比如 `cat ~/.ssh/id_rsa` 虽然命令头是 `cat`，但读的是工作区外
> 的敏感文件，所以不能直接放行。看不准的就降级成普通命令，交给用户确认。

### 被追问「最值得讲的设计点」

> 我觉得有两个。第一个是能力跃迁：接入 MCP server、安装 skill、创建定时任务，这些不一定
> 立刻删东西，但会改变 agent 后续能做什么，所以任何模式都要问。第二个是审批后重算 effect：
> 审批和执行之间隔着人的点击，如果执行前发现 effect 和审批时不一样，就拒绝执行，避免用户
> 批准的是 A，最后执行成 B。
