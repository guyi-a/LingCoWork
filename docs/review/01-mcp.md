## 主线（先握骨架，再下钻）

**问题**：agent 能力靠内置工具，扩展要等发版，用户无法自助。

| 层 | 解决什么 | 一句话 |
|---|---|---|
| 一 · 接上协议 | 工具从哪来 | 实现 MCP 客户端，任何服务自助接入 |
| 二 · 让普通用户能用 | 远程服务要登录 | 授权压缩成「点一下」，凭证进系统钥匙串 |
| 三 · 跑得快且稳 | 注入与调用被耦合 | 清单缓存 + 懒连接 + 连接池 + 错误分类 |
| 四 · 不牺牲安全 | 开放生态引入风险 | 不信自报注解，能力跃迁必确认 |

**延伸**：这套能力反过来喂给 agent 自己——用户一句话「接入 deepwiki」，agent 自己完成添加、探测、授权。

## 零 · 协议背景速查（10 行，够用即止）

- MCP 是 Anthropic 2024 底提出的开放标准，把「工具从哪来」标准化。类比：**MCP 之于 agent 工具，相当于 USB 之于外设**。
- 和 function calling 是**不同层**：function calling 解决「模型怎么表达调用」，MCP 解决「工具从哪发现、怎么调用」。**模型完全不知道 MCP 存在**——客户端是翻译层：向 server 拿工具清单翻译成 function calling 喂给模型，模型说要调 X，客户端翻译回 `tools/call` 转发。
- 消息层是 JSON-RPC 2.0（为什么不是 gRPC：工具**运行时才知道**，协议必须自描述；模型消费的本来就是文本）。设计血缘是 LSP——同样是「N × M 组合爆炸」的结构。
- 传输：stdio（本地子进程）/ Streamable HTTP（远程，当前推荐）/ 旧 HTTP+SSE（兼容）。旧方案被换掉的原因：双端点长连接难伺候代理和负载均衡。我们的实现自动协商：HTTP 优先、失败回退 SSE（`client.ts:44` connectAnyTransport；回退也失败时抛**原始 HTTP 错误**——SSE 的失败信息没有诊断价值）。
- **诚实边界**：wire 层（JSON-RPC 编解码、传输握手）用 `@ai-sdk/mcp` 实现，没手写。自研的是授权体验、凭证安全、连接管理、审批集成。主动说清，别揽。

## 一 · 接上协议

**决策 1：配置用文件，不用数据库。**
`~/.klingwork/mcp.json`，格式与 Claude Desktop / Cursor 兼容。理由：可 diff、可备份、可手改救急、可从别的客户端直接复制。数据库只存运行时状态（加密凭证），配置与状态职责分开。
真实历史动机：早先配置在数据库里，schema 严格校验，**一条脏数据打死整个 connectors 列表**；改文件后容错解析，坏的那条单独标出，其余照常（`config-file.ts:64`，读取永不抛异常，返回 `{servers, issues}`；写入区分 blocking / per-entry）。
追问「静态 API key 为什么明文」：和 Claude Desktop、Cursor 一致的产品取舍——用户需要能手改；只有 OAuth 凭证（程序自动获取、用户从来看不到）走加密。如实说是取舍，别硬圆。

**决策 2：工具名适配，宁可名字难看也不丢工具。**
模型 API 硬约束：`[A-Za-z0-9_-]`、最长 64、全局唯一；而 server 名是用户随便填的（可中文）。处理链路四步（`slug.ts`、`tools.ts:80`）：
① server 名转 ASCII 前缀——合法的直接放行（零开销），中文转拼音，转不了的取 8 位 sha256（跨进程稳定）；
② 远程名消毒（非法字符换 `_`）；
③ 超长截断 + **原始名**的 8 位哈希——截断后前缀相同的两个名字靠哈希仍可区分；
④ 数字后缀去重，同时避开内置工具名。
两个易讲错的点：`__` 分隔符**不是为了反向解析**（调用时靠闭包捕获 server 和 remoteName，不从名字拆）；撞名就改名，**绝不静默丢工具**。

**30 秒口头版**：
> 配置是文件单一事实源、容错解析，坏一条不影响其余；工具名做了适配层满足模型 API 的字符和长度约束，原则是宁可名字难看也不丢工具。

## 二 · 让普通用户能用（OAuth）

难点不是 OAuth 本身，是**用户不懂 OAuth**——他只知道「我要接入 Figma」。目标是压缩成「点一下授权，浏览器点个同意，回来就能用」。

**链路一步讲完**：连接返回 401 → 探测认证方式（三态：免认证 / OAuth / 静态 token，`oauth.ts:266`）→ 动态客户端注册拿 client_id（RFC 7591）→ 带 PKCE + state 发起授权 → 本机回环回调收 code → 换 token → `safeStorage` 加密落 SQLite → 自动重连。

Go 版时序（TS 版差异见对照表）：

```text
前端                后端                        provider
 │ POST authorize   │                            │
 │─────────────────▶│ discovery、注册、state/PKCE │
 │◀─────────────────│ auth_url                   │
 │ window.open(auth_url) ───────────────────────▶│
 │                  │        用户登录、点同意      │
 │                  │ 302 → /mcp/oauth/callback?code&state
 │◀─────────────────────────────────────────────│
 │ GET callback ────▶│ 校验 state、换 token、存库、
 │                  │ 自动重连、返回 HTML          │
 │ 轮询状态 → connected                            │
```

**追问弹药**（每条一两行，被问再展开）：

- **为什么删掉「认证方式」下拉框**：能从协议推断的信息不该让用户填——401 响应本身就是协议定义的信号。
- **为什么必须动态注册**：MCP 特有——客户端不知道用户明天连什么 server，不可能挨个预注册 client_id。注册结果要**持久化**，否则每次重启留一堆孤儿 client、用户反复 consent。
- **PKCE 防什么**：授权码被截取。桌面回调走本机回环，同机恶意程序可能截走 code——verifier 原值从没离开过客户端进程，截到 code 也换不到 token。公开客户端（`token_endpoint_auth_method: "none"`）因为桌面应用保守不了 secret，所以必须配 PKCE。
- **回环回调三细节**（`mcp-oauth-loopback.ts:113`）：绑 `127.0.0.1` 不绑 `0.0.0.0`（局域网打不进来）；端口传 0 让系统分配（防占用/抢注）；一次性（收到即关、5 分钟超时、重复回调 410）。
- **拒绝明文降级**（`mcp-secrets.ts:18`）：`safeStorage` 不可用时宁可授权失败也不明文落盘——数据库文件是普通文件，任何同用户进程都能读走；钥匙串是操作系统管的访问控制。允许降级，安全属性形同虚设。
- **刷新**：提前 60 秒（时钟偏移），并发刷新用 in-flight map 去重（防止把 refresh token 用废）；刷新失败清 token 强制重新授权，工具调用拿到结构化错误返回给模型，对话不崩。
- **Go 版回调为什么不同**：TS 桌面版无常驻进程只能临时起 loopback；Go 版后端常驻，固定路由 `/mcp/oauth/callback`（`oauth.go:15`）——provider 精确比对 redirect_uri，临时端口注册一次后永久被拒。回调返回 **HTML 不是 JSON**——访问者是浏览器导航不是 fetch。
- **前端为什么轮询而不是回调**：前端点完按钮进 `awaitingAuth`，后端授权成功自己重连，状态一变前端就看到。

**30 秒口头版**：
> 授权体验的目标是用户点一下。401 自动探测认证方式，OAuth 全流程动态注册加 PKCE，回调走本机回环，token 用系统钥匙串加密落盘、拒绝明文降级。授权完成自动重连，用户不用再做任何操作。

## 三 · 跑得快且稳（简历第二条 bullet，最能体现工程思考）

**优化前的问题**：每轮对话把所有 enabled server 全连一遍、结束全关。两个症状：stdio 子进程每轮重启（活动监视器肉眼可见）；绝大多数 server 这轮根本没被调用，成本白付。
**根因**：把「让模型看到工具」和「能调用工具」耦合了——以为要让模型知道有这个工具，就必须先连上。

**决策 1：manifest 剥离 + 缓存 + 懒连接。**
从 server 拿到工具后只留名字、描述、参数 schema 三样纯数据，`execute` 故意丢掉（`tools.ts:33`）——**描述和执行解耦**：一个纯数据可缓存，一个有状态按需建立。注入工具时完全不需要连接（`app-runtime.ts:1211`），真正建连推迟到模型实际调用那一刻（`tools.ts:258`）。没被调用的 server 成本归零。
manifest 缓存**无 TTL**——工具列表变化频率极低，TTL 是拿确定成本换不确定收益；代价是 server 中途加工具要等配置变更或重启才知道。

**决策 2：连接池。**
用完不关、放回池子保温，空闲 2 分钟回收（`client-pool.ts:40`）。**为什么是两分钟**：审批场景——用户点完「允许」的续跑是全新 run，用完即关意味着每次审批确认都重新拉子进程握手；永远不关又是资源泄漏。两分钟正好接住背靠背使用。
三个设计点：
- **池 key 由配置推导**（`client-pool.ts:73`）：改配置 key 自然变化 = 自动换新连接，不用写「监听变更主动重连」。**OAuth token 刻意不进 key**——进了的话每次 token 刷新都作废全部健康连接。
- **引用计数**：borrow 加一、release 减一，减到零才计时关闭——并发调用共用连接时，一个失败不立刻关，防止杀子进程带死还在跑的兄弟调用。
- **并发建连去重**：多个调用同时借冷 server 只发起一次连接，后来的等同一个 promise。

**决策 3：错误分类。**
判据：**错误里有没有 JSON-RPC 数字错误码**（`tools.ts:194`）。有码 = server 活着、协议正常，只是这次调用有问题（参数/权限）——连接健康，原样抛给模型自己改；无码（进程退出、连接重置、流关闭）= 真连接故障，作废重借。
优化前不区分：业务报错也触发重连，**健康连接被反复踢掉**，还连累多路复用同一条连接的兄弟调用。
两个特判：**abort 最先判断**（用户点 Stop 的 AbortError 也没数字码，不特判就既作废健康连接又在已 abort 的 signal 上重试）；**只重试一次**（这条路径本质 at-least-once——请求可能已在 server 执行只是响应没回来，有副作用的操作不敢多试）。

**收益怎么讲**：没做正式压测，**别编数字**。定性：stdio 子进程从每轮重启变成常驻+空闲回收；复用省一次握手往返，远程场景几百毫秒量级；没被调用的 server 成本归零。被追问量化就承认「没做上线前后 P95 对比，回头看应该补」——承认加正确做法，比编数字安全。

**30 秒口头版**：
> 根因是「注入工具」和「调用工具」被耦合。拆开后工具清单是纯数据可缓存，注入不需要连接，调用那一刻才懒建连；连接进池子跨对话复用，空闲两分钟回收，正好接住审批续跑这种背靠背使用；错误按有没有 JSON-RPC 错误码分类，业务报错不再误伤健康连接，重试严格一次。

## 四 · 不牺牲安全

**实际策略（别讲错）**：MCP 工具调用的审批门槛**和网络请求同级**——只看目标是否私有网段（`policy.ts:76`）。auto 模式下 MCP 调用直接放行；stdio 永远非私有（它的风险在「添加 server」时已审批过一次）。

**决策 1：不信 server 自报的注解。**
协议允许 server 给工具标 `readOnlyHint` 等，我们的实现**根本不读**——注解是 server 自己报的，恶意 server 完全可以把破坏性工具标成只读。**一个不可信的自我声明，不应该成为放行的依据。** 与其做一个看起来有用实际能被绕过的判断，不如统一按网络请求门槛处理。这是「安全属性不能建立在不可信方自我声明上」的判断，本身就是好谈资。

**决策 2：能力跃迁必确认。**
添加/删除/启停 server、发起 OAuth、skill 安装卸载——这些**改变模型下一轮能做什么**，auto 模式下也必须问（`policy.ts:30`）。只读的列举、查状态、测连接走常规规则。skill 安装同类：装 skill 等于把陌生人写的文档放进模型下一轮会读的指令里。

**决策 3：fail-safe 不 fail-open。**
URL 解析失败按**私有**处理（`tools.ts:146`）——畸形 URL 不能成为绕过审批的后门。

**攻击面心里有数**：工具描述藏提示词注入（描述会拼进 prompt）、返回结果夹带指令、谎报注解。防线是多层的：注入内容有信任边界提示、审批卡展示实际参数、agent 被带偏后做危险动作仍撞审批、stdio 命令添加时逐字展示、HTTP 强制 HTTPS 并拦私有 IP。

**30 秒口头版**：
> 开放生态的安全原则是不信任自我声明：server 报的注解不读，管理类操作——加 server、装 skill——任何模式都要确认，因为它们改变模型下一轮的能力边界。工具调用本身和网络请求同级审批。畸形 URL 按私有处理，fail-safe 不 fail-open。

## 延伸 · agent 自管理 MCP

8 个 `mcp_*` 工具（add / list / enable / disable / remove / oauth / test…）。用户直接说「接入 deepwiki」，agent 自己加配置、探测认证、必要时发起授权——**正因为认证能自动探测，这件事才能交给 agent**。
细节：探测到需要 OAuth 或 key 的 server **先存 disabled**，授权完成再启用；免认证的握手成功直接启用——避免连不上的 server 挂着每轮报错。

## TS / Go 两版对照

同一套协议在两种宿主形态下，好几个决策是反的：

| 维度 | klingwork-app（TS/Electron） | LingCoWork（Go/eino） |
|---|---|---|
| OAuth 回调 | 一次性 loopback，随机端口 | 常驻后端固定路由 |
| 凭证存储 | 系统钥匙串，拒绝明文降级 | SQLite + 0600 + 日志脱敏 |
| 工具动态性 | 连接池 + manifest 缓存 | 每轮 BeforeAgent 中间件重新注入 |
| 工具暴露面 | 全局注册 + 白名单裁剪 | 只给 root supervisor，不给 sub-agent |
| 审批 | effect 分类 + privateHost | effect 推导 + 模型分类器兜底 |

差异都有原因：桌面应用无常驻进程只能临时起回调；后端常驻挂路由最省事。凭证的威胁模型不同（对外分发的桌面应用 vs 本地开发工具）——**别硬说两边一样安全，如实讲威胁模型**。eino 图编译后不可变、工具首轮冻结，所以只能每轮中间件重注入——同一个问题在不同框架生命周期约束下的两种解法。
两遍都做完的收获：**能清楚区分哪些是协议要求的、哪些只是宿主形态的选择**。

## 诚实的边界

被问到直接承认，别硬撑：

| 项 | 状态 |
|---|---|
| JSON-RPC wire 层 | 用 `@ai-sdk/mcp`，没手写 |
| 配置文件热监听 | 写了但没接线，改配置要重启/手动刷新 |
| `tools/list_changed` 通知 | 没实现，清单缓存只靠配置变更失效 |
| 按 server 分风险等级 | v1 明确不做 |
| 静态 API key 加密 | 没做，明文在 mcp.json |
| MCP 失败在对话里的呈现 | 只有 console.error，界面看不到 |
| 量化收益 | 没做压测对比 |

不知道的规范细节，标准答法：**「这块当时是照 MCP authorization 规范实现的，具体 RFC 编号记不全，但设计意图是……」——意图永远答得上，条文记不住不丢分。**

RFC 速查（被追问才用）：资源元数据 9728、授权服务器元数据 8414、动态注册 7591、原生应用 OAuth 8252、resource 参数 8707、撤销 7009。
