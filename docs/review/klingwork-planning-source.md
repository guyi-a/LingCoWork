# Klingwork规划
# 背景
由于可灵内部的办公效能相关的基建后续会自建，myflicker也会停止内部服务，所以需要内部的业务系统、办公协同系统，构建自己的提效工具
为什么不用Codex/Claude Code
Codex和Claude Code主要是服务编码场景，和内部的业务系统、办公效能系统并不打通，没有接入到可灵真实的办公环境中，工作的流程依然割裂：

|  |  |  |
| --- | --- | --- |
|  | Codex/CC能做 | Codex/CC不能做 |
| 研发开发demo，并接入SSO | 快速开发demo | 接入可灵SSO |
| 产品写市场分析、PRD，并快速发布到内网服务器 | 完成PRD | 发布到内网服务器 |
| 定时分析，推送到kim | 定时分析 | 推送到kim |
| 完善/发布云文档 | ❌ 不支持 |  |
| 完成某个项目，需要查阅内部审批、系统、开发文档 | ❌ 不支持 |  |
| 代码自动发布、部署 | ❌ 不支持 |  |
| 内部的OA系统 | ❌ 不支持 |  |

# 工作协同与成果共享
另外，目前来看，myflicker在团队协同侧，并没有做太多的支持，只是依赖青雀文档、kim本身的协同来完成协同的工作。
这里我们不止关心"一个人能用 Agent 做多少事"，还要关心Agent做出来的东西、攒下来的能力，怎么在同事之间传下去、用起来，不用每次都从零开始。
## 一、用户工作成果分享（Artifacts Share）
为什么要做：现在 Agent 产出的文档、图、PPT、报告都散在各自的会话和 CDN 链接里，聊完就找不到了，别人也看不到。同一个东西经常有人重复做一遍。把成果存下来、能搜到、能分享，就能少做很多重复活。
大体怎么做：
建一个统一的成果存放和检索的地方，把Agent产出的东西自动收进去（记上类型、作者、时间、标签）；
分享沿用现在已有的 KIM 卡片、CDN、云文档发布，补上"谁能看"的权限控制和团队内的搜索；
支持在别人的成果上评论、接着改。

## 二、技能分享（Skill Hub & Skill Share）
为什么要做：Skill 是把一件事的做法固化下来。一个人把某个内部流程封装成 Skill，如果只能自己用就太可惜了；能分享出去，别人装上就能用，一次做好大家都省事。

# 轨迹数据资产
为什么要做
团队用 Agent 办公时，每一次交互都留下了一条完整的轨迹——用户提了什么需求、Agent 怎么一步步拆解和执行、调用了哪些工具、最后产出什么结果、用户满不满意、有没有返工。这些过程数据平时用完就丢，但攒起来是一份别处拿不到的资产：它记录了"在真实办公场景里，一个任务到底是怎么被完成的"。这类真实场景的 trace 数据，正是训练 Agent 能力最缺、也最难造的养料。
怎么做
在各办公场景里把交互轨迹结构化记录下来，形成「需求 → 执行 → 结果」的完整 trace（含用户意图、执行步骤、工具调用、产出、反馈）；
沉淀为可管理、可清洗、可标注的数据集，标注任务是否完成、结果好坏、返工原因；
反哺基础模型训练与评测，针对性提升 Agent 在真实办公场景的表现；
全程做好数据治理：采集前脱敏（去除个人隐私、敏感业务信息），按团队/场景分级授权，明确数据用途和留存期限，留可审计的使用记录，满足公司合规要求。

# 和 K-link 的结合
为什么要做
Agent 大量调用模型，token 用量、成本、预算这些必须管起来，尤其是团队维度——哪个团队用了多少、花了多少、预算还够不够、消耗集中在哪些场景。
K-link统一接入模型，整体外部模型接入可以复用，换模型加模型都不用改 Agent。
怎么做
模型调用统一走 K-link 的多模型接入，屏蔽底层模型差异；
复用它的团队 token 用量管理、计费、预算管理能力，按团队分账、设预算上限；
接入 token 用量分析，看清各团队、各场景、各时段的消耗分布，找出高消耗场景；
预算超限时可预警或限流，避免失控。

# 总结
功能上，我们解决的是"一个人能用 Agent 做多少事"——把技术文档、编码、OA、云文档、数据、定时推送、内容创作这些能力，让用户在日常办公里能直接用起来。
团队协同上，我们解决的是"做出来的成果、攒下来的能力和数据，怎么在团队里流转起来"：成果分享让别人做过的东西能被复用，技能分享让一次开发能全员受益。
基建上，我们通过MCP 接入把外部系统陆续接进来补齐缺口，轨迹数据资产把每天真实办公的过程沉淀成模型迭代的养料，和 K-link 的整合则把 token 成本和预算管起来，把账算清楚。
总结来看，我们需要先把个人提效做扎实，再往团队协同、数据沉淀和成本可控上走。
