## 一、为什么要做 KlingWork

可灵从快手拆分独立后，原来依赖的办公效能基础设施需要逐步自建，
MyFlicker 也将停止向可灵提供服务。这意味着原先通过 MyFlicker 使用的
云文档、内部知识、数据查询、定时推送和办公 Skill 等能力，需要在可灵体系内重新承接。

直接使用 Codex 或 Claude Code 不能完整解决这个问题。它们主要面向编码，
即使能够操作本地文件和执行命令，也难以直接纳入可灵统一的账号、内网、
权限和模型治理体系，更无法天然打通 KIM、云文档、天琴、OA 和数据平台等内部系统。

因此，可灵需要的不只是一个 Coding Agent，而是一套能够进入真实办公环境的
Agent 平台：

- 使用可灵自己的身份与权限体系
- 通过 KLink 统一接入和管理模型
- 将内部系统逐步转换为 Agent 可以调用的能力
- 同时覆盖研发、产品、运营等不同岗位的日常任务

> **KlingWork 是承接原 MyFlicker 办公提效需求、面向可灵自建的 Agent 办公桌面平台。**
> 它以对话和本地工作区为入口，让 Agent 调用模型、操作文件、执行任务并使用内部系统，
> 最终把结果以文档、代码、图片、视频等形式交付给用户。

## 二、KlingWork 承接什么，现在能做什么

KlingWork 承接的不是 MyFlicker 的代码，而是它背后的**办公能力生态**。
目前已经完成核心办公场景的承接，并在此基础上继续扩展可灵内部系统。

### 1. 模型与账号体系

- **KLink**：统一接入不同模型，并逐步复用用量统计、计费和预算管理能力
- **SSO / OBO**：让 Agent 以用户身份访问内部系统，而不是绕过原有权限体系
- **权限与审批**：模型可以提出操作，但高风险动作仍由用户确认

这一层解决的是：模型从哪里来、以谁的身份做事、使用成本和操作权限如何管理。

### 2. 内部知识与协作系统

当前已经接入的能力包括：

- 阅读和搜索 KStack 技术文章、内部开发文档
- 读取、创建和评论云文档与云表格
- 查询个人或团队知识库
- 通过 KIM 发送消息、提醒和任务结果
- 查阅项目审批、业务系统和内部规范

它的价值不是单独完成一篇文档，而是让 Agent 能读取内部资料、完成处理，
再把结果写回原来的办公系统，避免用户在多个平台之间来回复制。

### 3. 研发与执行环境

当前桌面端已经具备本地工作区、文件操作、Shell 执行、联网和浏览器等基础能力，
可以用于：

- 阅读和修改代码、运行构建与测试
- 根据需求生成 Demo、网页和技术文档
- 通过浏览器访问暂时没有 API 的内部系统
- 生成文件并在应用内预览结果

后续还需要继续接入代码仓库、天琴 CI/CD、部署平台和机器学习训练平台，
让 Agent 从“生成代码”进一步走向“完成研发流程”。

### 4. 办公与数据场景

KlingWork 已经覆盖内部知识查询、云文档协作、数据分析、定时推送和内容创作等场景：

- 文档撰写、数据整理、市场分析和 PRD 生成
- 业务指标查询、看板分析和 SQL 辅助
- 定时执行分析任务并将结果推送到 KIM
- 会议室、行政服务等内部 OA 操作
- 图片、PPT、网页等内容创作与分享

所以 KlingWork 不是只服务研发人员。写代码是其中一个场景，
产品、运营和其他业务人员同样可以通过 Agent 完成日常办公任务。

### 5. 能力扩展生态

内部系统很多，而且会持续变化，不可能全部写死在应用里。
KlingWork 通过四类方式扩展能力：

- **内置工具**：文件、命令、联网、用户交互和媒体生成等基础动作
- **Skill**：描述一类任务应该怎样使用工具，支持安装和复用新的工作流程
- **MCP**：把内部系统或外部服务按统一协议暴露为模型工具
- **浏览器能力**：在系统暂时没有 API 时，通过网页读取信息或完成操作

这四类能力共同解决“新的业务系统怎样低成本接入 Agent”的问题。
Skill、MCP 和浏览器不是三个独立产品方向，而是不同的能力接入方式。

## 三、KlingWork 技术上怎么实现

整体可以分成四层理解。

### 1. 桌面产品层

KlingWork 使用 Electron 构建桌面应用。用户创建对话，可以挂载本地工作区，
添加文件作为上下文，并在右侧面板预览 Markdown、代码、Office、PDF 和媒体文件。

桌面层还负责保存会话、展示任务状态、管理模型和连接器，
把底层 Agent 能力组织成用户真正可以操作和交付成果的产品。

### 2. Agent 运行层

一次任务不是模型生成一段文字就结束，而是持续执行：

```text
组装上下文
  → 调用模型
  → 模型选择工具
  → 执行工具并返回结果
  → 模型根据结果继续判断
  → 直到生成最终回答
```

为了让这个循环能够稳定运行，系统还实现了：

- **流式输出与事件持久化**：实时展示过程，刷新或切换会话后仍能恢复
- **审批**：危险操作先暂停，用户确认后再继续
- **上下文压缩**：长对话接近模型窗口上限时压缩旧历史
- **子 Agent**：把独立任务交给单独上下文处理
- **后台任务**：图片、视频等长任务异步执行，完成后再带结果续接原对话

### 3. 能力接入层

模型不会直接访问文件、数据库或内部系统，所有真实操作都通过工具完成：

- 通用基础动作由内置工具提供
- 固定工作流程由 Skill 提供
- 标准化外部系统通过 MCP 接入
- 缺少接口的网页场景由浏览器能力补充

这样的分层让 Agent Runtime 保持稳定，同时允许业务能力持续增加。

### 4. 数据与安全层

会话、消息、任务和配置在本地持久化，保证应用重启后可以恢复状态。
工具参数还会经过路径限制、权限判断和审批，避免模型仅凭提示词获得无限执行权限。

未来接入内部系统后，还需要复用 SSO / OBO 身份、服务端权限和审计机制，
确保 Agent 的操作与用户本人拥有的权限保持一致。

## 四、后续为什么还要继续建设

当前已经完成**个人提效**的基础能力建设：用户可以通过 Agent 使用内部能力，
处理编码、文档、数据和内容创作任务。

第二阶段走向**团队协同**：

- 将 Agent 生成的文档、图片、报告等 Artifacts 统一保存、搜索和分享
- 将个人沉淀的 Skill 发布给团队复用，减少重复开发
- 支持权限控制、版本管理、评价和使用统计

第三阶段形成**数据与成本闭环**：

- 将真实办公任务中的需求、执行步骤、工具调用和结果沉淀为轨迹数据
- 用这些数据支持 Agent 评测和模型能力优化
- 通过 KLink 统计模型用量、成本和预算，控制团队级资源消耗

因此，KlingWork 的长期方向不是继续堆单个工具，而是从个人提效入口，
逐步发展成可灵内部的 Agent 能力平台。

## 面试时怎么回答

### 被问“为什么要做 KlingWork”

> 可灵从快手拆分后，原来依赖的 MyFlicker 和办公效能基建将不再继续开放。
> Codex、Claude Code 虽然能处理编码任务，但很难直接进入可灵真实的办公环境，
> 例如使用内部身份访问 KIM、云文档、天琴和数据平台。因此我们需要自建一套
> Agent 办公平台，既承接原来的办公提效需求，也能够继续接入可灵自己的业务系统。

### 被问“KlingWork 能做什么”

> KlingWork 以对话和本地工作区为入口，Agent 可以操作文件、执行命令、联网、
> 使用 Skill 和 MCP，并生成文档、代码、图片、视频等交付物。它不只面向编码，
> 还已经支持内部知识查询、云文档协作、数据分析、定时推送和内容创作等办公场景。

### 被问“技术上怎么实现”

> 产品使用 Electron 构建桌面端，在本地运行 Agent 的模型—工具循环；
> 通过内置工具、Skill、MCP 和浏览器接入外部能力，同时用流式事件、审批、
> 上下文压缩、子 Agent 和后台任务保证复杂任务能够持续、可控地执行。

### 被问“你主要做了什么”

> 我主要参与能力扩展，包括 MCP、SkillHub、公共 Skill 以及 browser-use /
> browser-bridge；另外在运行机制上做了长耗时任务异步化，让图片、视频等任务
> 不阻塞当前对话，完成后能够自动把结果带回原会话。

## 项目边界（被追问再说）

- **krow**：上一代产品形态，本地 FastAPI sidecar 承载 Agent；
  browser-use、browser-bridge、应用广场和积分等能力主要在这条线
- **klingwork-app**：当前 Electron 桌面端，Agent 在主进程运行并使用 SQLite 本地持久化；
  重点是本地工作区、Agent Runtime 以及 Skill / MCP 能力生态

商业化、服务端部署和不同仓库的演进属于追问层，
不应该出现在“KlingWork 为什么存在”的第一轮回答中。
