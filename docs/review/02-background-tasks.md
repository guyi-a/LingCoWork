## 一句话

> 一张任务表，加一个进程内的调度器。
> 工具把任务写进表就立刻返回，这一轮对话正常结束。
> 调度器从表里取活、控制同时跑几个，跑完把结果写回对话。
> 应用重启就从表里把没跑完的捞出来接着跑。

面试先说这四句，然后停住，等他挑一个点问。

## 为什么要有它

Agent 跑起来是一个同步的循环：模型说要调工具，工具执行，结果回给模型，模型接着说
下一句。工具执行那段时间，这一轮就停在那里。

大部分工具几百毫秒就回来了。视频生成要几十分钟。如果工具就在那儿等着：

- 这一轮对话卡死，用户问不了别的
- 进程一关，这次生成就没了，重开也找不回来

图片生成也慢，十几秒到一分钟，程度轻一些，道理一样。

所以把「发起」和「等待」拆开：工具只发起，立刻返回；等待交给后台；等完了再把结果
送回对话。

## 三个零件

| 零件 | 干什么 |
|---|---|
| **任务表** | 记住现在有哪些任务在跑、跑到哪一步了 |
| **调度器** | 真的去等：排队、控制同时跑几个、推进状态 |
| **送回对话** | 结果写回会话，并自动起一轮新的，让模型接着干 |

为什么要用表，不用内存里一个数组：应用会关、会崩。表是唯一能跨进程活下来的东西。
后面「重启之后」那节全建立在这上面。

## 调度器在干什么

它手上有两份名单：**等着的**，和**正在跑的**。

只做一件事：看看等着的名单里，有没有任务现在可以开始。可以就启动，不可以就让它
继续等。

启动一个任务，就是把它从「等着」挪到「正在跑」，把表里的状态改成运行中，然后叫
干活的那个人去干。调度器自己不干活——它不知道视频是怎么轮询、怎么下载的，只等一个
结果回来。

任务结束，它把这个任务从「正在跑」划掉，把结果写进表，然后再看一遍等着的名单。刚才
腾出了一个位置，下一个可以进来了。

所以它是自己驱动自己的：跑完一个就叫下一个。名单空了就停，直到有新任务进来。没有
定时器，也没有人在那儿一直轮询。

**「可以开始」的判断，就是看同类任务跑满了没有。** 子 Agent 最多同时 3 个，视频最多
2 个。分开算是因为一个视频要占将近一小时——要是和子 Agent 抢同一批位置，那一小时里
子 Agent 全进不来，而子 Agent 通常几十秒就完事了。

**任务不一定一跑就跑到底。** 两种情况它会被放回「等着」的名单：账号还没登录，或者
网络临时出错。这两种都不算失败，只是现在跑不了。放回去之前先从「正在跑」里退出来，
把位置让给别人——一个在等登录的任务不该占着名额，它什么都没在做。

## 跟着一个视频任务走一遍

**① 工具先往表里写一行**，然后才去创建远程任务。

顺序是故意的。创建远程任务这一步会真的产生一个远端资源，如果先创建后落库，进程在
中间挂掉，本地就完全不知道这件事发生过了。

**② 创建的结果有三种。** 成功就把远程任务 ID 记到那行上，交给调度器；被明确拒绝就
把那行删掉，因为什么都没发生；**超时最麻烦——你不知道远端到底建没建**，所以行留着
当证据，但标记成不再通知对话，失败由这次工具调用本身告诉模型。

**③ 工具返回**，模型收到「任务已提交」，这一轮结束。用户可以马上聊别的。

**④ 调度器给它一个位置**，位置满了就排着。

**⑤ 干活的那个人开始跑**：轮询远端状态，渲染完了下载，写到用户指定的路径。每推进
一步都回写表，所以界面能实时显示在干什么。

**⑥ 完成后回到对话**：结果写进会话，并且自动起一轮新的 run。模型这时看到「视频好了、
在哪个路径」，就能接着做后面的事，比如把它插进正在写的文档里。

最后这一步是「后台任务」和「普通异步接口」的区别：不是等用户下次说话才告诉他，是
主动把对话往下推一步。

## 重启之后

应用重启，两份名单都空了。表还在。那表里那些没结束的任务怎么办？

分两类，**分界线是「要干的活还在不在表里」**。

**视频能接着跑。** 它排队的时候，队列里只存了一个任务 id。真正要干的活全在表那一行
里——远程任务 ID、跑到哪一步了、文件要写到哪。所以重启后把行捞出来重新排队，就能
接着跟。

**子 Agent 和图片不能，只能如实标成中断。** 它们排队的时候，队列里存的是**一个函数**
——具体怎么干装在那个函数里。进程一死，函数没了，表里那行再完整也没人知道该干什么。

图片还多一层原因：那个接口是同步返回图片本体的，没有远程任务 ID。所以异步化在图片
这里只为了不占住对话，不承诺能恢复。这个边界是想清楚了才划的，不是没做完。

还有个细节：**重启时视频只排队，不立刻开跑。** 这时候应用大概率还没登录完，凭证是
空的。立刻跑就会因为「没凭证」失败——为了一个一秒后就到的 token 把任务判死，是最坏
的答案。

## 被追问怎么答

每条都是独立的，答完就停。

**Q：并发怎么控制的？**
按类型分开算，子 Agent 3 个、视频 2 个。视频占位置太久，不能和子 Agent 抢同一批。

**Q：状态怎么存的？**
表里两个字段。一个说任务还活着吗（排队/运行中/完成/失败/取消/中断），另一个说它
活在哪一步（创建中/等登录/渲染中/下载中/写盘中）。拆成两个是因为：等登录时状态得回
到「排队」才能把位置让出来，但界面要能区分「排队等登录」和「排队等位置」。

**Q：临时失败会重试几次？**
不限次数，只有任务自身的期限。因为次数用完就等于放弃一个已经在远端跑着的任务，
而多等一会儿不花什么代价。

**Q：用户手动停止了怎么办？**
报错信息里带上远程任务 ID。服务商没有「列出我的任务」这种接口，这个 ID 是找回那个
视频的唯一路径，模型后面可以拿它恢复。

**Q：同一个远程任务会不会被两个本地任务同时追？**
远程 ID 上有数据库唯一索引，只在活跃状态内生效。

**Q：结果送回对话这步会不会失败？**
会，所以做了两层兜底。一是续跑失败要能回滚，让结果之后还能再送一次；二是启动时对
一遍账，补「任务完成了但通知没发出去」那个窗口。

## 如果他想聊「为什么不用现成的」

这个问题答好了很占便宜。

服务端场景的标准做法是消息队列加 worker：Celery、Sidekiq、BullMQ 这类。排队、重试、
并发全是框架的事，业务代码只写一个函数。更现代的是持久化执行，比如 Temporal——你写
看起来同步的代码，运行时把每一步结果记下来，进程挂了重放到断点继续。那种方案里
「状态机」根本不用手写。

但这些都要一个常驻的服务端或者中间件。我们是 Electron 桌面应用，没有服务端，也不能
要求用户先装个 Redis。

真正该对标的是 **Android 的 WorkManager**：SQLite 存任务、声明式约束（要有网络、要在
充电）、退避策略、同一个任务不重复排。我们做的事情形状几乎一样，只是把「要有网络」
换成了「要已登录」。Electron 没有等价物，所以只能自己写一个最小版本。

这段话同时说明三件事：知道标准方案、知道为什么用不了、知道自己写的东西在对标什么。
