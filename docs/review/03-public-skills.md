# 方向二 · 公共 Skill 的发现与安装（klingwork-app）

> 代码位置：搜索 `packages/app-runtime/src/public-skills/registry.ts`，
> 定位 `resolver.ts`，安装 `installer.ts`，
> 四个工具 `packages/agent-core/src/tools/skill-admin/`，
> 审批策略 `packages/agent-core/src/approval/policy.ts`。
>
> 越往后越细。读到哪儿都能停。

---

## 一句话

> 接了 skills.sh 这个公共技能市场。模型在对话里能搜、能先看文档、确认有用再装。
> 装进来的技能和本地技能一样被发现，下一轮就能用。
> 安装必须用户点确认，任何模式都跳不过去。

## 为什么要做

技能就是一个目录，里面一份 `SKILL.md`，教模型怎么把已有的工具用好。

之前技能只能靠人工引入：谁想加一个，得有人去写、去合、去发版。用户自己有需求就只能
等。而公共生态里已经有几千个现成的技能。

所以把这条路打通：**让模型自己去搜、自己判断、装进来**。用户说「帮我找个写周报的
技能」，它能真的去找。

## 三个动作，一条链路

| 工具 | 干什么 | 要不要审批 |
|---|---|---|
| `skill_search` | 在市场里搜，只返回列表 | 不用，纯读 |
| `skill_preview` | 把那个技能的 `SKILL.md` 正文拉下来看 | 不用，纯读 |
| `skill_install` | 下载整个技能包，写进技能目录 | **必须，任何模式** |
| `skill_uninstall` | 删掉装过的技能 | **必须，任何模式** |

工具描述里写死了顺序：**搜完必须先预览，不能直接从搜索结果装**。

为什么强制预览这一步：搜索的匹配是模糊的子串匹配，几乎总能返回东西，所以「搜到了」
根本不代表「对上了」。要判断这个技能到底在教什么，只能看它的正文。

**预览必须把正文回给模型**，不能只给描述和文件清单。因为这时候技能还没落盘，本机不
存在任何可读的文件——之前只给清单，模型想看内容就只能猜一个本地路径去 `read_file`，
然后撞一个文件不存在。

## 搜索是从哪里搜的

搜的是 **skills.sh**，一个第三方的公共技能索引站。它自己去收录 GitHub 上那些带
`SKILL.md` 的仓库，**只做索引，不托管文件**——文件始终留在各自的 GitHub 仓库里。

请求就一个：

```
GET https://skills.sh/api/search?q=frontend+design
```

无鉴权，不用配 key，10 秒超时。返回的每条带一个 `id`（形如
`anthropics/skills/frontend-design`）和来源仓库。

所以整条链路一共碰三个外部来源，各管一段：

| 来源 | 负责什么 |
|---|---|
| **skills.sh** | 搜索索引：给出「有哪些技能、id 是什么」 |
| **jsDelivr** | 仓库文件清单：这个技能在仓库里由哪些文件组成 |
| **raw.githubusercontent.com** | 文件内容：真正把文件下载下来 |

这三段是刻意分开的，后面「难点」那节会说为什么清单和内容要走两条路。

值得注意的是 skills.sh **不是我们的服务**，是社区的第三方站点。我们依赖一个自己不
控制的索引——这也是为什么解析它的响应时要写得那么防御。

接口本身很简单，真正的工作量在**摸清上游的实际行为**，以及**教模型怎么搜**。

摸出来的几条，都影响了实现：

- **一次固定返回 100 条，而且没有 limit 参数。** 所以条数只能本地截断，默认给 20 条。
- **支持按 owner 过滤。** 用户说「要 anthropics 官方那个」时用得上。
- **有些条目不在 GitHub 上**（比如以文档站域名为来源的）。这些当前装不了，所以搜索
  结果里会**标出来**——不标的话模型会拿去装，再失败一次。

解析响应时只声明我们真正用到的字段，其余全部剥掉。安装数那个字段声明成可选的——上游
哪天少给一个字段，不该让整页搜索直接失败。

错误分成两类：**我们的问题**（关键词为空、4xx）和**上游的问题**（超时、5xx、返回的不是
合法 JSON）。结构和预期不符时会明说「接口可能已变更」，因为那通常真的是上游改了，
而不是这次请求有问题。

## 更麻烦的是教模型怎么搜

这几条都是实测撞出来的，最后写进了工具描述里：

**必须用英文查询**，不管用户是用什么语言问的。这个生态是英文索引的，中文查询不会返回
空——会返回一堆维护更差的仓库，那比空结果更坏。

**不要传整句话。** 超过三四个词，命中就开始跑偏。给一两个领域名词就好，比如
`frontend design`、`weekly report`。

**匹配是模糊的子串匹配，而且几乎总能返回东西。** 搜 `excel` 会连 `code-review-excellence`
一起命中。所以「有结果」完全不能当成「找对了」——判断相关性只能靠预览。这就是为什么
链路上强制要先预览。

**好几个不相关的技能经常同名。** 而名字同时又是安装目录名，所以同名的里面只能装一个。
因此搜索结果必须报完整的 `owner/repo/skill`，只说名字没用。

**优先看 owner 认不认识，而不是看安装数。** 这是个安全取向：装技能等于让人写你的
指令，`anthropics` 这种可辨识的来源比一个下载量高但没人认识的仓库更可信。

这块我觉得值得单独讲——它不是写代码，是把「上游到底是什么行为」摸清楚之后，把结论
变成模型能照着做的规则。

## 难点不在下载，在「从一个 id 找到那几个文件」

这块是真正花时间的地方。

市场只做发现：搜索返回一个 id，形如 `owner/repo/skill`，**不给文件**。要装它，得自己
去 GitHub 把那几个文件找出来。而这里有三个坑。

**坑一：不能用 GitHub 官方 API。** 未鉴权额度是 60 次/小时，而且**按出口 IP 共享**。
公司走 NAT 出口，实测本机只剩 8 次——等于没有。

**坑二：不能整仓下载。** 有的仓库超过 25 MB，而我们只要里面一个 8 KB 的 `SKILL.md`。

**解法：清单和内容走两条路。**

- **文件清单**走 jsDelivr 的仓库接口：无鉴权，不占 GitHub 额度
- **文件内容**仍然回 `raw.githubusercontent.com` 取

这个区分是有意的：清单错了，最坏结果是装不上；**内容源换成第三方 CDN，才是把信任链
交出去**。所以只有清单那一步用第三方。

**坑三：id 末段不一定是目录名。**

`owner/repo/skill` 里的 `skill` 是技能**声明**的名字（`SKILL.md` 里写的 `name`），
不是它在仓库里的目录名。惯例上两者一致，但作者可以刻意分开——比如用目录名区分版本、
用声明名做对外的安装名。

所以定位分两步：

1. 先按目录名找：仓库里有没有一个叫这个名字、且直接含 `SKILL.md` 的目录
2. 找不到，才去下载候选目录的 `SKILL.md`，读里面声明的 `name` 对比

第二步有节制：只在第一步一无所获时才走，按目录深度从浅到深试（技能一般都在 `skills/`
下面），最多试 24 个，每批 8 个并发，超过 512 KB 的文件直接跳过——那不像一份文档。

顺带还有个小坑：**不带分支名拿不到默认分支**，所以按顺序试 `main` 再试 `master`。

## 安装做了哪些防护

装一个技能等于把陌生人的文件写进本机目录，所以每一步都设了限。

**路径**：拒绝 `..`、反斜杠、控制字符、空目录名、过长的名字、以空格或点结尾的名字。
这些都在拼出真实路径**之前**就拒掉。

**大小写冲突**：macOS 默认文件系统不区分大小写，包里同时有 `SKILL.md` 和 `skill.md`
会互相覆盖，装出来的东西和仓库里不一致。宁可拒绝。

**体积**：单文件 2 MB、总共 8 MB、最多 200 个文件、目录最深 5 层。而且
`content-length` 可能缺失或者撒谎，所以按**实际收到的字节数**复核。

**逐个下载，不并发**。技能包普遍就几个文件，并发省下来的时间不值得放弃确定的失败
顺序——出错时你知道是卡在哪个文件上。

**可执行文件黑名单**（`.exe`、`.so`、`.dll`、`.dmg` 这些）。文件清单里只要出现一个
黑名单后缀，**整个技能包立即拒绝，任何文件内容都不下载**；不是跳过该文件后继续安装。
静默删掉其中一个文件会改变上游包，而且剩余内容可能根本不能工作。这一条的理由要诚实讲：
这些东西**不会自己运行**，拦下来的安全收益接近零。真正的风险是 `SKILL.md` 指挥 Agent
去跑脚本，而那只能靠安装前的人工审批兜住。拦它们是因为技能包里出现可执行二进制本身
就说明拿错了东西，而且不想让技能目录变成投递落地点。

**元数据校验**：用和「扫盘发现技能」完全同一套规则校验。这样装进去的技能**必然能被
发现**，不会出现装好了但扫不出来的情况。

**撞名一律拒绝，不改写包的内容。** 和内置技能同名、目录已存在，都直接拒。不去自动
重命名，因为 `SKILL.md` 里的 `name` 必须等于目录名，改一处就得改另一处，而正文里
到处引用自己的名字——重写等于篡改别人的技能。

**原子生效**：先下载到同一个根目录下的临时目录，全部就绪后一次 `rename` 换过去。
要么完整出现，要么完全没有，模型不会读到半个技能。临时目录必须和目标同一个文件
系统，`rename` 才是原子的。

顺带：`rename` 如果因为目录被占而失败，按「撞名」报错，不能笼统说「未知错误」。

## 卸载只删自己装的

技能目录是共用的——里面还躺着仓库自带的内置技能，以及其他来源装的东西。误删了用户
不一定恢复得回来。

所以安装时会在目录里写一个记录文件，卸载的判据只有一条：**有没有这个记录**。没有就
拒绝，并说清这是谁的地盘。

记录里还存了内容的 sha256。**锁内容而不锁 commit**，因为同一个 commit 里技能目录可能
根本没变，换了 commit 也可能只改了仓库里别的技能。判断「要不要更新」只有内容说得准。

## 为什么安装必须强制审批

装一个技能，是把一份陌生人写的文档放进技能目录，**从下一轮开始它就是模型读的指令的
一部分**。这是能力跃迁，和给 Agent 加一个远程服务同级。而且这个市场没有任何人审核。

所以它和「加一个 MCP server」放在同一档：**任何模式都必须问人，包括全自动模式**。

工具描述里还写明了两句话，都是怕模型说岔：

- **装进来不等于可以跑**。技能里带的脚本，运行时照样走正常的命令审批。
- **装完这一轮用不上，下一轮才行**。技能是每轮开始时扫盘发现的，别假装立刻能用。

## 被追问怎么答

**Q：审批的时候展示什么？**
只放从 id 就能推出来的东西——id 和技能名。因为审批通过之后系统会重算一遍这个描述并
要求完全一致，而文件数、体积、哈希都得先下载才知道，放进去必然对不上。文件清单和
描述由预览那一步在对话里交代。

**Q：为什么不做更新，只能卸载再装？**
没有更新工具。原因是「要不要更新」得靠内容哈希比对，而比对之前得先下载——那和重装
没区别。先卸再装语义更清楚。

**Q：搜索结果里有装不了的怎么办？**
市场里存在以域名为来源的条目（比如某个文档站），它们不在 GitHub 上，当前装不了。
搜索照样返回，但会标出来——不标的话模型会拿去装再失败一次。

**Q：这条链路和内网技能市场什么关系？**
两套东西，共用技能格式和安装目录，但注册中心、入口、安装器、安全策略都不同。最大的
区别是**谁发起安装**：内网市场是用户在界面上点的，用户的点击本身就是授权；公共技能是
模型自己搜、自己决定装哪个，那是模型在替用户做决策，必须让用户确认。

同一个动作，发起者不同，安全模型就不同。
